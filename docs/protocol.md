# AD-5664 子機の無線プロトコル

A&D の熱中症指数モニター AD-5664SET の子機（AD-5664-01）が親機へ送っている電波の形式を、RTL-SDR で受信して解析した結果です。

> **非公式の資料です。** メーカーは仕様を公開していません。ここに書いた内容は、受信したデータと子機の画面の値を照らし合わせて推定したものです。株式会社エー・アンド・デイとは関係ありません。

各項目の「状態」の意味は次のとおりです。

- **確定**: 実測値や子機の画面の値と一致することを確かめた
- **ほぼ確定**: 計算値や実測値とよく合うが、子機の画面とはまだ照合していない
- **未確定**: まだわかっていない

## 1. 早見表

| 項目 | 値 | 状態 |
|---|---|---|
| 周波数 | 429.20 MHz（取扱説明書の値）。**CH1〜5 で共通** | 確定 |
| 変調 | 2値 FSK、偏移 約 ±11 kHz。周波数が高い側が `1` | 確定 |
| ビットレート | 10,000 bps（1ビット = 100 µs）、NRZ | 確定 |
| プリアンブル | `AA AA …`（`1010…` が約 64 ビット） | 確定 |
| 同期語 | `2D D4` | 確定 |
| データ長 | 同期語の後ろに 17 バイト（固定） | 確定 |
| チェックサム | byte 0〜15 の合計の下位 8 ビット = byte 16 | 確定 |
| 1回の送信 | 約 22 ms のパケットを、約 11〜16 ms の間をあけて **3回** くり返す | 確定 |
| 送信間隔 | CH1 121 秒、CH2 123 秒、CH3 125 秒、CH4 127 秒、CH5 129 秒。電池を入れた直後の 2 分間は約 15 秒ごと | 確定 |

```
CH        = byte[0] >> 5
湿度 [%]  = byte[3]
温度 [℃] = ((((byte[5] & 0x0F) << 8) | byte[4]) − 500) / 10
WBGT      = ((byte[9] << 8) | byte[10]) / 10
VH [g/m³] = ((byte[11] << 8) | byte[12]) / 10
次の送信まで [秒] = (((byte[15] << 8) | byte[14]) + 1) / 8
正しいパケット: (byte[0] + … + byte[15]) & 0xFF == byte[16]
```

`byte[n]` は、同期語 `2D D4` の直後のバイトを `byte[0]` として数えます。

## 2. 物理層

### 2.1 周波数

- 取扱説明書によると、使う周波数は 429.20 MHz の 1 つだけです。CH は周波数ではなく、**送信間隔をずらして**混信を防いでいます。
- 実際に、受信の設定を変えずに子機の CH を 1〜5 と切り替えても、信号はどれも同じ位置に見えました。
- 解析に使ったドングル（チューナーが Fitipower FC0013 のもの）では、**受信の設定によって、信号が最大 1 MHz 近くずれた位置に見えました**。たとえば `-f 429.9M -s 2400k` では 429.906 MHz、`-f 429.3M -s 1024k` では 428.887 MHz に見えました。
  - このため、付属のプログラムは **2.4 MS/s の広い幅で受信し、FFT で信号の位置を探してから復調します**。
  - 動作を確かめた設定は `-f 429.9M -s 2400k` です。R820T など別のチューナーでは、429.2 MHz 付近に正しく見える可能性があります（未確認）。

### 2.2 変調と速度

- FM 復調した波形が 2 つの周波数の間を行き来することから、FSK だとわかりました。偏移は約 ±11 kHz です。
- プリアンブルのエッジ 50 個の位置に直線を当てはめて、1 ビットの長さを 100 µs（10,000 bps）と求めました。
  - 最初はエッジの間隔を整数のサンプル数で数えて、9,600 bps と見誤っていました。4 % の違いでも短い区間なら正しく読めてしまうため、`0` や `1` が長く続く所で初めてビットの取りこぼしとして表れました。

### 2.3 送信のタイミング

```
|<- パケット1 (約22ms) ->|  休み (約11ms)  |<- パケット2 ->|  休み (約16ms)  |<- パケット3 ->|
```

- 3 つのパケットの中身は同じです（3 つとも 17 バイトすべてが一致します）。
- 送信の間隔は CH ごとに 2 秒ずつ違い、`121 + 2 × (CH − 1)` 秒です。
- 電池を入れた直後の 2 分間は、約 15 秒ごとに送信します（byte 2 のフラグが立ちます）。
- 子機の赤い LED が点滅するのが、送信のタイミングです。
- 子機の液晶は送信より細かい間隔で更新されます。画面の値と受信したデータを照らし合わせるときは、**赤い LED が点滅した直後の画面を読む**必要があります。

## 3. パケットの構造

```
[プリアンブル AA AA … 約8バイト] [同期語 2D D4] [データ 17バイト]
```

| バイト | 例 | 内容 | 状態 |
|---|---|---|---|
| 0–1 | `2A F7` | 子機の ID（16 ビット）。**上位 3 ビットが CH 番号**で、残りの 13 ビットは電池を入れ直すたびに変わる | 確定 |
| 2 | `00` / `20` | フラグ。`20` は 15 秒ごとの送信モード中（電池を入れた直後の 2 分間。ただし最初と最後の 1 回は `00`）。ほかのビットは未確認 | ほぼ確定 |
| 3 | `32` | 湿度 [%]。値そのまま（0x32 = 50 %） | 確定 |
| 4 | `12` | 温度の下位 8 ビット | 確定 |
| 5 | `03` | 下位 4 ビットが温度の上位ビット。上位 4 ビットはこれまで常に 0 | 下位は確定 |
| 6–8 | `00 00 00` | これまで常に 0。別売りの温度プローブを使うときの欄かもしれない | 未確定 |
| 9–10 | `00 EC` | WBGT × 10（ビッグエンディアン。0x00EC = 236 → 23.6） | ほぼ確定 |
| 11–12 | `00 8D` | VH（容積絶対湿度）× 10 [g/m³]（ビッグエンディアン。0x008D = 141 → 14.1） | ほぼ確定 |
| 13 | `00` | これまで常に 0 | 未確定 |
| 14–15 | `C7 03` | 次の送信までの時間 × 8 − 1（リトルエンディアン、1/8 秒単位）。0x03C7 = 967 → (967 + 1) / 8 = 121 秒 | ほぼ確定 |
| 16 | `AB` | チェックサム。byte 0〜15 の合計の下位 8 ビット | 確定 |

### 3.1 温度

```
raw  = ((byte[5] & 0x0F) << 8) | byte[4]
温度 = (raw − 500) / 10   [℃]
```

- 0.1 ℃ 単位の値に 500 を足して（50.0 ℃ ずらして）送っています。
- 例: `12 03` → raw = 0x312 = 786 → (786 − 500) / 10 = **28.6 ℃**
- 0 ℃ より下の温度はまだ確かめていません。この式のとおりなら、raw = 0 が −50.0 ℃ です。また、温度に使われるのが byte 5 の 4 ビットなのか 2 ビットなのかも、まだわかっていません（0〜40 ℃ の範囲ではどちらでも同じ結果になります）。

### 3.2 ID と CH

```
byte[0]                   byte[1]
b7 b6 b5 b4 b3 b2 b1 b0   b7 … b0
|-- CH --|  |------- ランダム（13 ビット）-------|
```

| 子機の CH | 受信した ID の例 | byte[0] の上位 3 ビット |
|---|---|---|
| CH1 | `26 13`、`2A F7`、`2A 75`、`20 1B` | `001` |
| CH2 | `43 19`、`48 E1` | `010` |
| CH3 | `61 C5`、`60 17` | `011` |
| CH4 | `89 F5`、`88 19` | `100` |
| CH5 | `AF 7D` | `101` |

- 電池を入れ直したりリセットしたりすると、下位 13 ビットが新しい値になります。親機は「電波サーチ」でこの ID を覚え直すのだと考えられます。
- 受信プログラムでは、**`byte[0] >> 5` で CH を見分ける**のがおすすめです。こうすると、電池を交換して ID が変わっても、同じ子機として扱えます。
- 近くに同じ製品があって同じ CH を使っていると、CH だけでは区別できません。その場合は ID 全体で区別してください。

### 3.3 WBGT と VH

- 子機の画面に出る WBGT（暑さ指数）と VH（容積絶対湿度）は、子機が自分で計算して送っています。受信側で計算する必要はありません。
- VH は、温度と湿度から計算した値と ±0.2 g/m³ 以内で一致しました。
- WBGT は温度・湿度と一緒に変わりますが、環境省の簡易推定式で計算した値より 0.2〜0.6 低くなりました。子機がどの式を使っているかはわかっていません。
- どちらも、子機の画面の値とはまだ照合していません。

### 3.4 次の送信までの時間（byte 14–15）

- ふだんは CH ごとに決まった値です: CH1〜5 で `03C7` / `03D7` / `03E7` / `03F7` / `0407` → 121 / 123 / 125 / 127 / 129 秒。これは実測した送信間隔と一致します。
- 送信が 0.1 秒ほど遅れた回は、`03D6`（122.875 秒）のように 1 小さい値を送っていました。そして実際に、次の送信は 122.89 秒後に来ました。決まった値ではなく「次の送信までの時間」を送っていて、遅れた分を次の回で取り戻しているようです。遅れの原因は、ほかの子機の電波とぶつからないように待つ「キャリアセンス」だと思われます。
- 15 秒ごとの送信モードのときにどんな値になるかは、まだ確かめていません。

### 3.5 パケットの例

```
2A F7 00 32 12 03 00 00 00 00 EC 00 8D 00 C7 03 AB
```

この例は、CH1、湿度 50 %、温度 28.6 ℃、WBGT 23.6、VH 14.1 g/m³、次の送信まで 121 秒、という意味です。チェックサムは 0x2A + 0xF7 + … + 0x03 = 0x3AB で、下位 8 ビットが `AB` になり一致します。子機の画面の値（28.6 ℃ / 50 %）とも一致しました。

受信した 40 種類の正しいパケットを、[tests/data/packets.txt](../tests/data/packets.txt) に収めてあります。

## 4. 照合した記録

| データ（byte 0–5） | 計算した値 | 子機の画面 |
|---|---|---|
| `2A F7 00 32 12 03` | 28.6 ℃ / 50 % | 28.6 ℃ / 50 % |
| `2A F7 00 30 0E 03` | 28.2 ℃ / 48 % | 28.2 ℃ / 48 % |
| `2A F7 00 2E 0C 03` | 28.0 ℃ / 46 % | 28.0 ℃ / 46 % |

- 子機 5 台（CH1〜5）を同時に動かして 14 分間記録したところ、50 回の送信をすべて受信できました。3 回のくり返しも、すべて一致しました。
- 記録した 150 パケットは、すべてチェックサムが一致しました。

## 5. 復調の方法（付属のプログラム）

`src/ad5664/demod.py` で行っている処理です。

1. 2 ms ごとの平均の振幅から、送信している区間（約 0.1 秒）を見つける。
2. 区間ごとに FFT で信号の中心周波数を求め、0 Hz に移す。そのあと間引いて FM 復調し、7 点のメディアンフィルタでノイズのとげを取り除く。
3. **振幅**を使って、3 回のくり返しを 1 パケットずつに切り分ける。パケットの**終わりは削らない**（削ると最後のチェックサムのバイトが欠けます）。
4. プリアンブル部分の平均値を、0 と 1 の境目にする。プリアンブルのエッジから 1 ビットの長さを測り、各エッジの位置を「最初のエッジからの時間 ÷ 1 ビットの長さ」で丸めてビットの境目を決める。こうすると誤差がたまらないので、`0` や `1` が長く続いてもビットを取りこぼさない。
5. 同期語の後ろの 17 バイトを取り出し、チェックサムが合わないものは捨てる。残ったくり返しの多数決をとる。

### 5.1 rtl_433 について

rtl_433 の flex デコーダでも、ある程度は受信できました。

```
rtl_433 -f 429.905M -s 250k -Y minmax -R 0 \
  -X 'n=AD5664,m=FSK_PCM,s=100,l=100,g=10000,r=20000,preamble={24}aa2dd4,bits>=120'
```

解析のときは、ビットレートを見誤ったまま `s=104,l=104` で使っていました。上の `s=100,l=100` に直した設定は、まだ試していません。`-f` の値は、2.1 節のドングルのずれに合わせて変える必要があります。

また、次の問題がありました。

- 出力が 1 ビット前後ずれることがある。
- `1` が長く続く所で、パケットの途中から 1 ビットずれることがある。
- `-s 2400k` にすると、何も出力しなくなった。
